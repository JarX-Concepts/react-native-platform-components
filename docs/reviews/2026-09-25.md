# Package review — 25 September 2026

Reviewed version **1.4.0**, starting at `e90bc59`, with fixes on
`fix/package-quality-review`. This review covers the TypeScript API, native
iOS/Android implementations, web controls, Expo plugin, packaging, examples,
documentation and CI. This report records validation before the pull request;
no package release was published.

## Remaining findings and clear feature gaps

### 1. Refresh and triage development dependencies before release

The full workspace audit returned **116 entries**: 2 critical, 77 high,
33 moderate and 4 low. Counts include multiple advisories per package and
some deprecation notices; they are not 116 demonstrated exploit paths.
The root package's production-dependency scan returned no advisories. The
published library has no ordinary runtime dependencies; consumer-supplied
React/React Native versions need their own assessment.

Examples requiring attention are `shell-quote@1.8.3`
([object-token command injection advisory](https://github.com/advisories/GHSA-w7jw-789q-3m8p))
and `tar@7.5.2`
([unbounded input advisory](https://github.com/advisories/GHSA-23hp-3jrh-7fpw)).
These appear in the development/tooling graph. Refresh compatible transitive
versions, inspect remaining dependency paths and test the build/release tools.
The native fixes do not change the JavaScript dependency lockfile. Reachability
of every reported advisory was not audited.

### 2. Complete web keyboard navigation

`src/web/SegmentedControl.tsx`, `ButtonGroup.tsx`, `TabBar.tsx`,
`NavigationRail.tsx` and the modal `SelectionMenu.tsx` support ordinary focus
and activation but lack the expected arrow-key movement and managed tab stops.
SelectionMenu also lacks typeahead. Browser testing confirmed that an arrow key
did not move a selected segment.

Add a shared keyboard/focus policy with disabled-item skipping, Home/End,
orientation and RTL handling; test it against real DOM controls. The
[WAI tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) and
[radio-group pattern](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) define
the expected interactions. The current limitation is now documented.

### 3. Fill the intentional web menu gaps

Web ContextMenu is a passthrough. Button menu actions, SplitButton's menu and
ButtonGroup overflow menus are not implemented on web. These are documented
fallbacks, but they prevent full feature parity for a shared application UI.
An accessible DOM menu implementation would be a meaningful next feature;
click/keyboard, dismissal, focus return, disabled actions and nested menus
need coverage together.

### 4. Add disabled options to SelectionMenu

SelectionMenu has whole-control disabling but no per-option `disabled` field,
unlike segmented, button-group and context-menu items. This prevents showing
an unavailable choice while retaining it in context. It requires coordinated
TypeScript/codegen/native/web support and accessibility tests.

### 5. Finish the cross-platform icon contract

`PlatformIcon` has iOS/Android alternatives but no web alternative. Native SF
Symbols and drawables have no browser equivalent; image assets are the portable
choice. A web source or documented fallback API would help icon-only controls.

Native normalization forwards an image URI and scale, but drops headers and
other request options accepted by `ImageURISource`. Authenticated image URLs
requiring custom headers therefore do not work as native icons. This is now
documented; supporting them needs an explicit native request contract.

### 6. Make selection identifiers explicit

Native SelectionMenu and SegmentedControl reserve the empty string as the
no-selection sentinel. Public strings did not previously communicate that
restriction. Documentation and type comments now require unique, non-empty
values. A development warning or a separate native `hasSelection` field would
make misuse easier to diagnose or allow true empty-string values.

### 7. Add durable browser and visual regression coverage

The existing Jest web tests run through React Native mocks. They could not
detect the real inherited `aria-disabled` problem or browser event/constraint
semantics. Keep a small RN Web fixture in the repository with browser CI for
keyboard, focus, forms and dialogs. Add selected screenshot baselines across
light/dark themes and large text/RTL instead of relying solely on recordings.

DateRangePicker's absence on iOS is an explicit platform limitation, not a
newly discovered broken implementation. Continue using two DatePickers there
unless the project chooses to maintain a custom range picker.
